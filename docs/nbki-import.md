# Импорт исторических выгрузок НБКИ

Первый этап модуля работает с источником `QY01GG000001` (ИНН `4307012081`), XML схемы 5.1.
Исходные файлы с персональными данными не хранятся в Git. Импортер сохраняет их сжатые копии
и SHA-256 в базе CRM, а также реестр событий и пар «договор — УИД».

Перед импортом примените миграцию `V0130__nbki_import_registry.sql`. Затем выполните:

```bash
DATABASE_URL='...' python backend/nbki_import.py \
  --xml /secure/import/20260824.xml \
  --xml /secure/import/20260902.xml \
  --xml /secure/import/20261006.xml \
  --receipt /secure/import/20261006_ticket1.zip \
  --receipt /secure/import/20261006_ticket2.zip
```

Без `--apply` расчет выполняется в транзакции и откатывается. После проверки итоговых счетчиков
повторите команду с `--apply`. Повторный запуск не создает дубли.

Без серверной консоли администратор может выполнить тот же импорт во вкладке
«Администрирование → НБКИ»: выбрать XML-файлы и расшифрованные ZIP-квитанции,
затем нажать «Импортировать и сопоставить». Браузер сжимает XML перед отправкой;
сервер принимает только файлы нужного источника и версии схемы.

Сопоставление выполняется по точному номеру договора в рамках организации. Дополнительно
сверяются тип и имя заемщика, ИНН, дата рождения, сумма и дата договора при наличии этих полей.
Если поля расходятся или их недостаточно для проверки, УИД остается в реестре со статусом
`review` и не привязывается к займу. Отсутствующие в CRM номера имеют статус `not_in_crm`.
Импортер не изменяет существующие договоры и пайщиков.

Статус `accepted` отражает содержание загруженного `ticket2`. Поле
`receipt_signature_verified` остается ложным до проверки подписи квитанции локальной
утилитой CryptoPro. Если квитанции к файлу нет, его события не считаются подтвержденными.
Результаты доступны администратору на вкладке «Администрирование → НБКИ».

В промышленной среде сначала убедитесь, что исходные XML и квитанции помещены в закрытый
каталог, недоступный через Nginx. Закрытый ключ и PIN CryptoPro не передаются на сервер.

## Отчет событий 1С MXL

Во вкладке «Администрирование → НБКИ» можно загрузить отчет событий `.mxl`. Импорт сохраняет
все 1С-строки и непустые ячейки, разделяет УИД заемщиков и поручителей и не меняет сумму,
дату, график, остаток или платежи договоров CRM. УИД заемщика показывается в карточке
договора только после сверки номера, имени, суммы и даты. Если реквизиты расходятся,
связь остается на проверке. УИД поручителя не подставляется как УИД заемщика.

Для серверной проверки без записи и последующего импорта:

```bash
DATABASE_URL='...' python backend/nbki_mxl_import.py /secure/import/events.mxl
DATABASE_URL='...' python backend/nbki_mxl_import.py /secure/import/events.mxl --apply
```

Повторная загрузка того же файла идемпотентна. События имеют основание приема
`operator_assumed` — это допущение по указанию оператора, а не доказательство фактического
приема НБКИ. Оно не заменяет `ticket2` и проверку подписи квитанции через CryptoPro.

Кнопки «Excel · Проверить» и «Excel · Нет в CRM» выгружают XLSX с двумя листами: XML и MXL.
В таблицах рядом с реквизитами источника показаны доступные реквизиты CRM и оставлены
колонки для решения и комментария после ручной сверки. Таблица сама по себе не меняет CRM.

Кнопка «Excel · Без УИД» выгружает все договоры организации со статусами
`active`, `overdue`, `holiday`, которым еще не сопоставлен УИД заемщика. В файл
добавлены возможные УИД из XML и MXL и колонки для решения менеджера. Закрытые
договоры не включаются.

Если в MXL есть запись поручителя, импортер сверяет номер договора и имя с уже существующим
поручительством в «Обеспечении» и заполняет только пустые поля: имя, УИД, сумму и даты
поручительства. При неоднозначности запись остается без изменений. Поля залога из MXL
не заполняются, если соответствующий блок отчета пуст.

## Черновики исходящей выгрузки

Администратор может проверить займ по ID в разделе НБКИ и сохранить неизменяемый
снимок исходных данных в `nbki_outbox_drafts` (миграция V0134). Повторное
сохранение того же снимка идемпотентно. Кнопка «Черновики всех займов» делает
то же только для договоров со статусами `active`, `overdue`, `holiday`
(до 500 за один вызов). Закрытые договоры не включаются; ранее созданные
черновики закрытых договоров сохраняются для аудита со статусом `excluded`.
Проверка выявляет пробелы в реквизитах
договора и заемщика, расхождение или неоднозначность УИД. Спорные связи не
попадают в готовые файлы. Снимки не являются XML ГУТДФ, и их нельзя отправлять
в НБКИ. `submittable` всегда `false`, пока не реализованы полное сопоставление
событий CRM с блоками ГУТДФ, XSD и содержательная валидация по правилам НБКИ.
MXL-статус `operator_assumed` не превращается в подтвержденный прием.

Официальный архив XSD 5.1 Банка России:
`https://cbr.ru/Content/Document/File/185178/tech_5_1_19112025.zip`,
SHA-256 `f1d82275ffc4df9ade469e5ce365639cd83b0398429999d2b9d738ba9b8dc36e`.
Для отдельного, уже сформированного XML доступен валидатор:
На машине проверки нужен пакет Python `lxml` (`python -m pip install lxml`).

```bash
python scripts/nbki_validate_xml.py /secure/export/file.xml \
  --schema-zip /secure/reference/tech_5_1_19112025.zip
```

Он проверяет XSD, заголовок, УИД и счетчики, но не заменяет содержательные
правила НБКИ и квитанцию о приеме. Все три полученные исторические XML с
`schemaVersion=5.1` не проходят опубликованную XSD 5.1: в блоке `FL_28_Payment`
перед `payCurrency` схема требует `sizeCode` и `scheduleCode`. Это отдельное
расхождение формата, которое необходимо согласовать с НБКИ; даже наличие
квитанции к одному историческому файлу не делает его безопасным шаблоном для
новых выгрузок.

Для будущего этапа локальной подписи подготовлена утилита
`scripts/nbki_local_sign.py`. Она требует SHA-256 готового XML из журнала CRM,
проверяет байты перед подписью, вызывает локальный `cryptcp` для отсоединенной
подписи `.p7s` и проверяет подпись. Пример (только для **проверенного** XML):

```bash
python scripts/nbki_local_sign.py /secure/export/file.xml \
  --sha256 <64-символьный-хеш-из-CRM> \
  --schema-zip /secure/reference/tech_5_1_19112025.zip \
  --thumbprint <отпечаток-локального-сертификата>
```

PIN запрашивается CryptoPro интерактивно и не передается на сервер. Утилита не
создает архив, не шифрует и не отправляет файл: точный состав пакета и канал
передачи необходимо согласовать с НБКИ и испытать на локальной версии CryptoPro.
