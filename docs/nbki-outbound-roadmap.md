# Исходящая выгрузка НБКИ: правила допуска

Текущая реализация намеренно не выпускает файл для отправки. Снимки CRM и
исторические записи 1С не являются достаточным подтверждением содержания
нового события. Для XML используется технический формат Банка России 5.1,
применяемый с 01.07.2026: https://cbr.ru/ckki/poryadok-formirovaniya-kreditnoy-istorii/.
Нумерацию «ГУТДФ 7.0» в примерах НБКИ нельзя автоматически отождествлять с
версией официальной XSD 5.1.

## Матрица источников

| Данные | Источник в CRM | Статус для новой выгрузки |
| --- | --- | --- |
| Номер, дата, срок, сумма, ставка, тип графика, платёж по графику, текущий остаток | `loans` | Есть; проверить на дату события. `monthly_payment` не равен нормативному среднемесячному платежу |
| Субъект: ФИО, ИНН, дата рождения, паспорт, адрес | `members` | Частично есть; базовая проверка в `inspect_loan` |
| УИД договора | `nbki_deals` / `nbki_event_deals`, только однозначное `matched` | Не найден/спорный — блокировать |
| Фактические платежи | `loan_payments` | Есть, но изменение записи не обязательно означает новое событие |
| График и исполнение | `loan_schedule` | Есть; не равны подтверждённой детализации задолженности |
| Залог и поручительство | `loan_collateral` | Есть частично; УИД поручительства — отдельная связь |
| Коды вида, назначения, условий сделки | Исторические XML | Только контекст; для нового события нужны подтверждение и правило актуализации |
| Полная стоимость, среднемесячный платёж | Нет подтверждённого расчёта на дату события | Блокировать до реализации расчёта и сверки |
| Текущая/срочная/просроченная задолженность и даты | Не представлены как единый проверенный срез | Блокировать до сверки расчёта |
| Дата и время фактического события | Частично даты платежей; `updated_at` — время изменения записи | Не подменять временем записи CRM |
| Коды соблюдения размера/срока платежей ФЛ_28.10/28.11 | Письмо ЦБ от 09.12.2025 запрещает направлять с 29.12.2025; опубликованная XSD 5.1 всё ещё требует элементы | Не проставлять числовые коды; проверить представление прочерков по XSD и согласовать с НБКИ |

В карточке проверки займа можно открыть последний исторический XML 1С для
сопоставленного УИД. Выводятся коды сделки, ПСК, нормативный среднемесячный
платёж и показатели задолженности, если они есть в событии. Дата, статус
квитанции и факт проверки подписи показываются рядом. Эти значения **не**
переносятся автоматически в текущий XML: они могут относиться к прошлой дате,
а часть квитанций не имеет проверенной подписи.

Отчёт MXL, предоставленный 28.10.2026, содержит 703 события до
28.10.2026 13:28:28. Для однозначно сопоставленных действующих займов
показатели последнего события сохраняются в `nbki_1c_loan_facts` и видны во
вкладке договора «НБКИ / 1С». Каждое значение хранится вместе с номером
колонки, названием показателя, идентификатором источника и строкой исходного
отчёта. Это справочные значения 1С на дату события, не изменение учётных
полей `loans`, `loan_schedule` и `loan_payments`.

## Маршрутизация изменений

`nbki_change_candidates` связывает два неизменяемых снимка. Добавление платежа,
изменение графика, условий займа, заемщика, обеспечения и УИД получает
категорию для проверки. Это **не** присвоение кода ГУТДФ: по одному diff
невозможно доказать юридический факт и время события. Удаление или коррекция
старого платежа должно идти через отдельный сценарий исправления, а не как
новый платёж. Закрытые договоры исключаются из исходящего потока.

В официально предоставленном примере НБКИ для события 2.3 («изменение
задолженности, в том числе ввиду исполнения обязательства») одновременно присутствуют блоки задолженности и платежа.
Поэтому само наличие `FL_28_Payment` или изменившегося остатка не определяет
тип события; его устанавливает подтверждённое основание изменения.

## Порядок выпуска

1. По договору подтверждены УИД и все обязательные сведения для конкретного
   события; доступна дата фактического события и расчётный срез.
2. Сопоставлены код события и все обязательные/условные блоки официальной
   версии; проведены содержательные проверки суммы и дат.
3. Генератор фиксирует неизменяемые байты XML и SHA-256. Валидация официальной
   XSD и структурная проверка обязательны, но не заменяют п. 2.
4. XML скачивается и подписывается локальным CryptoPro по зафиксированному
   SHA-256. Ключ и PIN не передаются в CRM. По переданному регламенту НБКИ
   редакции 7 далее следуют ZIP-компрессия подписанного файла и шифрование
   ZIP на открытом ключе Бюро. Конкретный состав ZIP и команда шифрования
   проверяются на тестовом обмене; неподтвержденный пакет не отправляется.
5. Квитанция сверяется по регистрационному номеру и проверяется локально
   CryptoPro. Статус «принято НБКИ» возможен только по соответствующей
   квитанции `ticket2`, а не по MXL, `ticket1` или факту загрузки ZIP.

Пока не выполнены п. 1–2, кнопка генерации XML не должна появляться. Отчет
`readiness_report` показывает блокирующие пункты по всем действующим договорам.
# Сверка показателей 1С с CRM

Административный раздел НБКИ содержит read-only отчёт «Сверить с CRM» и Excel «Сверка 1С / CRM». Для каждого однозначно сопоставленного действующего займа он сравнивает дату окончания договора (ФЛ_18.11) и последний платёж (ФЛ_28.1/28.2) с CRM. Платежи CRM суммируются только за ту же календарную дату, не позднее даты события 1С. Несовпадение платежа — сигнал для ручной проверки, не основание автоматически менять учёт, считать событие отклонённым или формировать XML. Дата окончания в CRM отражает конец графика, а в 1С может обозначать срок договора, поэтому различие этих дат показывается отдельно, справочно, без включения в счётчик платёжных расхождений. Каждая строка Excel несёт УИД, дату события и номер строки исходного MXL.

Для уточнения платёжных расхождений отчёт ищет ровно один платёж той же суммы в пределах трёх дней от даты 1С либо точную сумму платежей за два соседних дня. Такие совпадения помечаются только как кандидаты и сопровождаются ID платежей CRM; они не изменяют исходные записи и не считаются доказанным тождеством операций. Неоднозначные совпадения остаются в ручной проверке.

По прямому решению пользователя для шести названных УИД в сверке последнего платежа выбран учёт CRM. Решения хранятся отдельно в `nbki_1c_reconciliation_decisions`, привязаны к конкретной строке MXL и точным ID платежей. Они снимают только соответствующий вопрос о платеже; дата окончания договора остаётся справочным различием, а остальные показатели 1С сохраняются как история. При новом событии 1С или изменении состава/сумм платежей решение не применяется автоматически. Исходящие черновики и будущий генератор должны брать платежи из CRM, не из MXL; отправка XML по-прежнему заблокирована до полной проверки формата и правил.

Позднее пользователь установил общее правило для КПК «Эксперт Финанс»: все учётные значения для исходящей выгрузки берутся из CRM, включая оставшиеся пять платёжных расхождений и будущие события. MXL используется только для сопоставления УИД, восполнения отсутствующих справочных показателей с указанием источника и исторической сверки. Это правило не означает переноса сумм 1С в `loans`/`loan_payments`. Отчёт сверки сохраняет оригинальный статус различия, но помечает его разрешённым по общему правилу CRM. Шесть прежних адресных решений остаются аудитом, не ограничивают действие общего правила. Договоры без единственного сопоставленного УИД исключены из исходящей очереди.

Read-only очередь `payment_candidates` показывает платежи CRM с датой позже последнего события 1С по действующим займам с однозначно сопоставленным УИД. Платежи той же календарной даты не объявляются новыми без проверки времени события. Очередь не назначает код ГУТДФ и не выпускает XML; принятие MXL остаётся допущением пользователя, а не подтверждённой квитанцией.

Та же выдача отдельно показывает `schedule_due_review`: строки **текущего** графика со сроком после последнего события 1С и до сегодняшней даты. Это контроль слепой зоны платёжной очереди: согласно разъяснению Банка России от 21.03.2025, срок платежа, начисление процентов и возникновение просрочки сами могут образовывать событие 2.3, даже без фактического платежа; разные факты в один день могут требовать отдельных блоков. Строка текущего графика не доказывает, что такой срок действовал исторически, а совпадение с платежом не доказывает отсутствие отдельного события. Полное выявление ежедневных начислений и просрочки пока не реализовано; численность списка не следует считать количеством документов для отправки. Источник: https://www.cbr.ru/content/document/file/177310/20250321_44_19-2385.pdf.

Для строк с текущим статусом `overdue` и непогашенной суммой отдельно выводится возможная дата перехода в просрочку — следующий календарный день после **эффективного** срока, перенесённого по применяемому в CRM правилу выходных и фиксированных праздников. Это ориентир для проверки, **не** утверждённая дата возникновения просрочки: прошлые изменения графика и платежи должны быть восстановлены по первичным документам. Проверка порядка графика выявляет повтор номера платежа и переход к более ранней дате при росте номера.

По договору CRM № `100-000000824062025` подтверждены сохранённые в CRM кредитные каникулы с 01.04 по 01.07.2026 (3 месяца) и запись аудита `set_holiday` от 23.04.2026. Код CRM при оформлении каникул помечает строки № 10–12 как `holiday` и добавляет три новые строки № 25–27 после существующего графика № 1–24; поэтому даты новых строк в августе–октябре 2026 года идут **после** строки № 24 с датой 28.06.2027. Это документированная структура, созданная каникулярной функцией CRM, а не доказательство случайной порчи порядка строк. Для проверки событий строки надо сортировать по датам и учитывать происхождение: строка № 27 со сроком 01.10.2026 не имеет платежа в CRM, но её условия и исторический расчёт задолженности не подтверждены неизменяемым снимком. Учётные строки автоматически не исправляются, XML заблокирован до полной сверки.

Дополнительная консервативная проверка сравнивает остаток займа с **нижней оценкой** непогашенного основного долга по открытым строкам: из планового основного долга каждой строки вычитается вся уже зачтённая сумма, включая проценты. Материальный избыток более 1% остатка (минимум 1 ₽) помечается для ручной проверки; мелкие расхождения остаются предметом точной сверки распределений. По этому договору открытые строки содержат 65 150,58 ₽ планового основного долга, нижняя оценка после вычета зачтённого — 63 150,58 ₽ против 33 351,88 ₽ остатка займа. Такой график нельзя использовать для расчёта ФЛ_25–29 без сверки каникулярного соглашения и порядка построения добавленных строк. Автоматического исправления нет.

Для таких платежей очередь указывает **кандидат** кода 2.3 по разделу 5 приложения 3 к Положению Банка России № 758-П («изменились сведения об исполнении обязательства субъектом»). Это не утверждённый код события: необходимо исключить исправление старой операции, подтвердить момент платежа и весь обязательный набор блоков. Поле `gutdf_event_code` остаётся пустым, `event_code_confirmed=false`.

Очередь также показывает покрытие денежной ветви `FL_Event_2_3` из официальной XSD 5.1: 16 прямых блоков, включая условные. Перечень сверен автоматическим тестом с архивом XSD по зафиксированной SHA-256; `FL_22`, `FL_29` и `FL_29_1` остаются условными в XSD, но отдельные требования делают их обязательными для определённых потребительских займов. Наличие реквизитов CRM в блоке 17 не означает проверку XML. Из учёта CRM доступны предварительный остаток основного долга, его разделение на срочную и просроченную части для последнего платежа и накопленные платежи. Фактически начисленные проценты, пени и ВСП пока показываются как отдельные кандидаты с условиями применимости; итоговая задолженность ФЛ_25–28 не утверждена. Ни один кандидат пока не готов к XML.

Для каждого кандидата очередь вызывает существующую предварительную проверку `inspect_loan`: если обнаружен конфликт УИД, кандидат исключается; иначе показываются недостающие реквизиты и блокирующие пункты для XML. Это проверка покрытия данных, не XSD-валидация и не доказательство корректного расчёта на дату платежа.

Внутренний контроль `nbki_accounting_snapshot` восстанавливает остаток основного долга непосредственно до и после конкретного платежа из первоначальной суммы займа и уже внесённых частей основного долга в журнале CRM. Он проверяет равенство суммы платежа его частям, отсутствие отрицательного остатка и, только для последней операции, совпадение вычисленного остатка с текущим `loans.balance`. Результат сопровождается ID платежа и не называется нормативной задолженностью ФЛ_25–28: начисленные проценты, сроки, просрочка и момент фактического события требуют отдельного расчёта и проверки.

Также на момент каждого платежа сверяются накопленные суммы по журналу CRM: всего, основной долг, проценты и пени. Они дают проверяемое основание для дальнейшего расчёта блока ФЛ_28, но сами по себе не являются значениями ФЛ_28: для него ещё нужны правила агрегации, кодов соблюдения размера/срока и сверка с нормативной методикой.

Для платежей единого движка v2 дополнительно сверяются неизменные строки `loan_payment_allocations`: суммы по процентам, плановому и досрочному основному долгу, пене и нераспределённой части должны совпасть с записью платежа. Проверяются ссылки на строки графика того же займа. Это доказательство внутреннего разнесения CRM, но не исторический нормативный срез по ФЛ_25–28. Текущий `loan_schedule` меняется при перерасчётах и не должен задним числом приниматься за его состояние в день старого платежа.

С 29.10.2026 новые платежи v2 сохраняют `nbki_recorded_at` — момент регистрации в CRM с часовым поясом. Это **не** дата и время наступления события. Для ручных обычных и досрочных платежей оператор может дополнительно указать подтверждённое фактическое время приёма в МСК; оно сохраняется отдельно в `nbki_event_occurred_at` с основанием `operator_entered`. Если время неизвестно, поле остаётся пустым. Прежние платежи не получили вымышленный backfill. Банковский импорт пока содержит только календарную дату (`operation_date` с техническим `00:00`), поэтому автоматически не утверждает точное время платежа.

Оператор отдельно сообщил точное фактическое время по платежам CRM 2649, 2652, 2656 и 2657 (10:42:15, 10:45:12, 10:46:18, 10:47:11 МСК соответственно). Миграция `V0142` привязала времена только к этим ID при совпадении организации, займа, даты и суммы. Основание в БД — `operator_entered`; время регистрации в CRM по-прежнему не считается временем события. Наличие времени не снимает другие блокировки XML.

Для каждого нового платежа движка v2 внутри той же транзакции сохраняется неизменяемый снимок займа и всего графика **до и после** проведения в `nbki_payment_posting_snapshots`, с SHA-256 канонического JSON. Это защищает исходные условия и результат платежа от последующего перерасчёта графика. Снимок отражает состояние CRM в момент проведения; для задним числом внесённого платежа он не доказывает историческое состояние на указанную дату. Старые платежи не получают искусственно восстановленных снимков. Он также не заменяет расчёт ФЛ_25–28.

С 29.10.2026 снимок расширен точными распределениями v2 по каждой строке графика и суммой уже оплаченной пени. При наличии нового снимка модуль проверяет SHA-256 и восстанавливает срочный/просроченный основной долг, просроченные проценты и остаток пени именно из состояния после проведения, даже если позже график изменился. Для платежей 2649, 2652, 2656, 2657 снимков нет: они созданы до включения механизма, и по ним остаётся только кандидат по текущему графику. Неизменяемый снимок нельзя создать задним числом из сегодняшних строк.

Для последнего платежа по договору `nbki_crm_debt` теперь восстанавливает по текущему графику CRM и точным распределениям v2 непогашенные части строк с уже наступившим сроком: просроченные основной долг и проценты. Разность между подтверждённым журналом остатком основного долга и его просроченной частью показывается как срочный основной долг. Для четырёх платежей 2649, 2652, 2656, 2657 после проведения просроченные части равны нулю. Более старые платежи этим путём не рассчитываются, потому что последующие операции меняют график.

Дополнительно только как кандидат рассчитывается фактически накопленный процент текущего периода по правилу действующего движка CRM `остаток основного долга × ставка × фактические дни / 365`, с учётом переходов остатка по журналу платежей и процентов, уже зачтённых в соответствующую строку графика. Кандидат не является утверждённым значением ФЛ_26.5: в CRM нет отдельной истории изменения ставки и подтверждённого условия договора о базе дней, а текущий график может быть пересчитан после события. В частности, сумму будущих процентов графика нельзя подменять фактически накопленной задолженностью; это разъяснено Банком России в письме от 22.12.2022 № 46-7-1/3613: https://www.cbr.ru/Content/Document/File/145761/20221222_46_7_1-3613.pdf. Полный блок ФЛ_25–28 и XML остаются заблокированы до содержательной сверки.

`nbki_debt_preview` складывает сверенный основной долг, просроченные проценты по графику, кандидат начисленных процентов текущего периода и остаток пени, подлежащей оплате в последнем периоде. Арифметическая сумма показывается отдельно как **предварительный баланс**, не как ФЛ_25–27: для старых платежей нет неизменяемого снимка на дату события, а учётная политика начисления процентов ещё не подтверждает нормативный момент возникновения требования. Модуль не меняет долговые поля XML и прекращает расчёт при несогласованных компонентах.

Пени в CRM накапливаются в `loan_schedule.penalty_amount`, а погашения — отдельно в `loan_payments.penalty_part`. Пользователь подтвердил, что они начисляются ежедневно и подлежат оплате с последним платежом по графику; кандидат показывает дату последнего платежа и остаток. Для старых платежей текущая начисленная сумма не доказывает её размер на дату события, поэтому XML остаётся заблокированным. Нормативное включение в блоки задолженности и ВСП требует отдельной сверки.

Для новых автоматических платежей движок v2 теперь удерживает уже начисленную и ещё не уплаченную пеню только при достижении последнего периода графика: после процентов и перед основным долгом. Пеня фиксируется отдельным компонентом распределения, не прибавляется к `loan_schedule.paid_amount`; текущие и старые платежи не переразносятся задним числом. При обычном платеже точно в день графика проценты не пересчитываются как при досрочном платеже до срока.

Письмо Банка России от 09.12.2025 № 44-19/8423 прямо запрещает формировать и направлять числовые показатели ФЛ_28.10 и ФЛ_28.11 с 29.12.2025: https://www.cbr.ru/Content/Document/File/185542/20251209_44_19-8423.PDF. При этом архив XSD 5.1 от 19.11.2025 объявляет элементы `sizeCode` и `scheduleCode` обязательными, но допускает значение «-» через `emptyValueType`. Исторические XML их опускали и не проходят опубликованную XSD. До тестового согласования с НБКИ нельзя самостоятельно назначать числовые коды или объявлять файл готовым.

Разовая проверка в памяти на историческом XML от 06.10.2026: вставка прочерков в 51 блок `FL_28_Payment` сняла ошибки по этим элементам в XSD 5.1; документ всё ещё имеет четыре другие ошибки схемы (пустой `calcDate`, два недопустимых `purposeCode=17`, неверная ветка элемента `rate`). Исходный файл не изменялся. Это подтверждает только техническую допустимость прочерка для XSD, а не согласие НБКИ принять будущий пакет или корректность содержательных полей.

Предварительный ВСП `nbki_smp` считается только из оставшихся после последнего платежа строк графика CRM при полном совпадении их непогашенного основного долга со срочным остатком журнала. Используется формула `(сумма будущих платежей / T) + просроченная задолженность`, округление вверх до целого рубля и календарное `T` по письму Банка России от 25.06.2024 № 44-8-1-1/2310: https://www.cbr.ru/Content/Document/File/161841/20240625_44_8_1_1-2310.pdf. Показываются варианты без пеней и с их включением в будущие платежи, а также с полным `T` и `T≤48`; ни один вариант не объявляется нормативным до подтверждения категории займа и договорного срока уплаты пеней. Письмо Банка России от 20.10.2025 № 44-19/7326 требует учитывать договорные платежи кредитору без произвольных исключений: https://www.cbr.ru/Content/Document/File/184537/20251020_44_19-7326.pdf.

Письмо Банка России от 20.02.2026 № 44-8-1/1069 требует отражать фактический момент события, а не момент формирования кредитной информации: https://www.cbr.ru/Content/Document/File/187264/20260220_44_8_1-1069.pdf. Указание `00:00:00+00:00` предусмотрено только для перечисленных в письме случаев, включая событие, которое законом или договором определено только датой. Для обычного платежа произвольное `HH:MM:SS+03:00` не является допустимым способом восполнить неизвестное время. Требуется согласовать подтверждённую методику для старых платежей и банковского импорта.
# ПСК по договорам CRM (29.10.2026)

Для действующих займов «Эксперт Финанс» с сопоставленным УИД введён расчёт ПСК по статье 6 Закона № 353-ФЗ. Денежные потоки восстанавливаются из первоначальной суммы, ставки, срока и типа графика CRM по тем же правилам, которыми CRM строит плановый график. Штрафы за нарушение договора исключены; по подтверждению оператора обязательных дополнительных платежей нет. Результат хранится отдельно от учётных сумм и виден в карточке займа.

Пользователь подтвердил потребительскую цель по договорам 105 и 143. По 143 исторический признак 1С «пополнение оборотных средств» является ошибочным. Решение записано в `nbki_loan_purpose_confirmations` с указанием источника; сырые сведения 1С не меняются. Это снимает только неопределённость цели, но не утверждает рассчитанную ПСК: 105 остаётся на проверке из-за расхождения процента, 143 — из-за отсутствия сопоставимого исторического расчёта.

Сверка с историческим показателем 1С выполняется только как контроль первоначальных условий. Статус `cross_checked` означает расхождение не более 0,020 процентного пункта и 1 рубля; это не подменяет подписанные условия договора и не разрешает XML автоматически. Статус `review` означает, что исторические условия не подтверждены или расхождение превышает порог. Текущий график не используется как исходный, так как он изменяется досрочными платежами и дополнительными соглашениями. В production: 39 расчётов, из них 22 `cross_checked`, 17 `review`. Подтверждённая пользователем потребительская цель договоров 105 и 143 не устраняет расхождения расчёта ПСК и необходимость сверки с подписанными условиями.

Код обычного разнесения платежа использует месячную ставку `годовая/12`; код крупного досрочного платежа текущего периода использует фактические дни/365. Пеня начисляется ежедневно и предъявляется к оплате в последнем платеже графика. В ПСК пеня не включается, а в регуляторной задолженности рассматривается отдельно. Для полной готовности событий 2.3 остаётся сверка моментного начисления процентов и обязательных кодов с данными CRM.
