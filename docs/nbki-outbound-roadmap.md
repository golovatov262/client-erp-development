# Исходящая выгрузка НБКИ: правила допуска

Текущая реализация намеренно не выпускает файл для отправки. Снимки CRM и
исторические записи 1С не являются достаточным подтверждением содержания
нового события. Для XML используется технический формат Банка России 5.1,
применяемый с 01.07.2026: https://cbr.ru/ckki/poryadok-formirovaniya-kreditnoy-istorii/.
Нумерацию «ГУТДФ 7.0» в примерах НБКИ нельзя автоматически отождествлять с
версией официальной XSD 5.1.

## Матрица источников

| Данные | Источник в CRM | Статус для новой выгрузки |
| --- | --- | --- |
| Номер, дата, срок, сумма, ставка, тип графика, платёж по графику, текущий остаток | `loans` | Есть; проверить на дату события. `monthly_payment` не равен нормативному среднемесячному платежу |
| Субъект: ФИО, ИНН, дата рождения, паспорт, адрес | `members` | Частично есть; базовая проверка в `inspect_loan` |
| УИД договора | `nbki_deals` / `nbki_event_deals`, только однозначное `matched` | Не найден/спорный — блокировать |
| Фактические платежи | `loan_payments` | Есть, но изменение записи не обязательно означает новое событие |
| График и исполнение | `loan_schedule` | Есть; не равны подтверждённой детализации задолженности |
| Залог и поручительство | `loan_collateral` | Есть частично; УИД поручительства — отдельная связь |
| Коды вида, назначения, условий сделки | Исторические XML | Только контекст; для нового события нужны подтверждение и правило актуализации |
| Полная стоимость, среднемесячный платёж | Нет подтверждённого расчёта на дату события | Блокировать до реализации расчёта и сверки |
| Текущая/срочная/просроченная задолженность и даты | Не представлены как единый проверенный срез | Блокировать до сверки расчёта |
| Дата и время фактического события | Частично даты платежей; `updated_at` — время изменения записи | Не подменять временем записи CRM |
| Коды соблюдения размера/срока платежей | Нет проверенного источника | Блокировать |

В карточке проверки займа можно открыть последний исторический XML 1С для
сопоставленного УИД. Выводятся коды сделки, ПСК, нормативный среднемесячный
платёж и показатели задолженности, если они есть в событии. Дата, статус
квитанции и факт проверки подписи показываются рядом. Эти значения **не**
переносятся автоматически в текущий XML: они могут относиться к прошлой дате,
а часть квитанций не имеет проверенной подписи.

Отчёт MXL, предоставленный 28.10.2026, содержит 703 события до
28.10.2026 13:28:28. Для однозначно сопоставленных действующих займов
показатели последнего события сохраняются в `nbki_1c_loan_facts` и видны во
вкладке договора «НБКИ / 1С». Каждое значение хранится вместе с номером
колонки, названием показателя, идентификатором источника и строкой исходного
отчёта. Это справочные значения 1С на дату события, не изменение учётных
полей `loans`, `loan_schedule` и `loan_payments`.

## Маршрутизация изменений

`nbki_change_candidates` связывает два неизменяемых снимка. Добавление платежа,
изменение графика, условий займа, заемщика, обеспечения и УИД получает
категорию для проверки. Это **не** присвоение кода ГУТДФ: по одному diff
невозможно доказать юридический факт и время события. Удаление или коррекция
старого платежа должно идти через отдельный сценарий исправления, а не как
новый платёж. Закрытые договоры исключаются из исходящего потока.

В официально предоставленном примере НБКИ для события 2.3 («изменились сведения
об обеспечении») одновременно присутствуют блоки задолженности и платежа.
Поэтому само наличие `FL_28_Payment` или изменившегося остатка не определяет
тип события; его устанавливает подтверждённое основание изменения.

## Порядок выпуска

1. По договору подтверждены УИД и все обязательные сведения для конкретного
   события; доступна дата фактического события и расчётный срез.
2. Сопоставлены код события и все обязательные/условные блоки официальной
   версии; проведены содержательные проверки суммы и дат.
3. Генератор фиксирует неизменяемые байты XML и SHA-256. Валидация официальной
   XSD и структурная проверка обязательны, но не заменяют п. 2.
4. XML скачивается и подписывается локальным CryptoPro по зафиксированному
   SHA-256. Ключ и PIN не передаются в CRM. По переданному регламенту НБКИ
   редакции 7 далее следуют ZIP-компрессия подписанного файла и шифрование
   ZIP на открытом ключе Бюро. Конкретный состав ZIP и команда шифрования
   проверяются на тестовом обмене; неподтвержденный пакет не отправляется.
5. Квитанция сверяется по регистрационному номеру и проверяется локально
   CryptoPro. Статус «принято НБКИ» возможен только по соответствующей
   квитанции `ticket2`, а не по MXL, `ticket1` или факту загрузки ZIP.

Пока не выполнены п. 1–2, кнопка генерации XML не должна появляться. Отчет
`readiness_report` показывает блокирующие пункты по всем действующим договорам.
# Сверка показателей 1С с CRM

Административный раздел НБКИ содержит read-only отчёт «Сверить с CRM» и Excel «Сверка 1С / CRM». Для каждого однозначно сопоставленного действующего займа он сравнивает дату окончания договора (ФЛ_18.11) и последний платёж (ФЛ_28.1/28.2) с CRM. Платежи CRM суммируются только за ту же календарную дату, не позднее даты события 1С. Несовпадение платежа — сигнал для ручной проверки, не основание автоматически менять учёт, считать событие отклонённым или формировать XML. Дата окончания в CRM отражает конец графика, а в 1С может обозначать срок договора, поэтому различие этих дат показывается отдельно, справочно, без включения в счётчик платёжных расхождений. Каждая строка Excel несёт УИД, дату события и номер строки исходного MXL.

Для уточнения платёжных расхождений отчёт ищет ровно один платёж той же суммы в пределах трёх дней от даты 1С либо точную сумму платежей за два соседних дня. Такие совпадения помечаются только как кандидаты и сопровождаются ID платежей CRM; они не изменяют исходные записи и не считаются доказанным тождеством операций. Неоднозначные совпадения остаются в ручной проверке.

По прямому решению пользователя для шести названных УИД в сверке последнего платежа выбран учёт CRM. Решения хранятся отдельно в `nbki_1c_reconciliation_decisions`, привязаны к конкретной строке MXL и точным ID платежей. Они снимают только соответствующий вопрос о платеже; дата окончания договора остаётся справочным различием, а остальные показатели 1С сохраняются как история. При новом событии 1С или изменении состава/сумм платежей решение не применяется автоматически. Исходящие черновики и будущий генератор должны брать платежи из CRM, не из MXL; отправка XML по-прежнему заблокирована до полной проверки формата и правил.

Позднее пользователь установил общее правило для КПК «Эксперт Финанс»: все учётные значения для исходящей выгрузки берутся из CRM, включая оставшиеся пять платёжных расхождений и будущие события. MXL используется только для сопоставления УИД, восполнения отсутствующих справочных показателей с указанием источника и исторической сверки. Это правило не означает переноса сумм 1С в `loans`/`loan_payments`. Отчёт сверки сохраняет оригинальный статус различия, но помечает его разрешённым по общему правилу CRM. Шесть прежних адресных решений остаются аудитом, не ограничивают действие общего правила. Договоры без единственного сопоставленного УИД исключены из исходящей очереди.

Read-only очередь `payment_candidates` показывает платежи CRM с датой позже последнего события 1С по действующим займам с однозначно сопоставленным УИД. Платежи той же календарной даты не объявляются новыми без проверки времени события. Очередь не назначает код ГУТДФ и не выпускает XML; принятие MXL остаётся допущением пользователя, а не подтверждённой квитанцией.

Для таких платежей очередь указывает **кандидат** кода 2.3 по разделу 5 приложения 3 к Положению Банка России № 758-П («изменились сведения об исполнении обязательства субъектом»). Это не утверждённый код события: необходимо исключить исправление старой операции, подтвердить момент платежа и весь обязательный набор блоков. Поле `gutdf_event_code` остаётся пустым, `event_code_confirmed=false`.

Для каждого кандидата очередь вызывает существующую предварительную проверку `inspect_loan`: если обнаружен конфликт УИД, кандидат исключается; иначе показываются недостающие реквизиты и блокирующие пункты для XML. Это проверка покрытия данных, не XSD-валидация и не доказательство корректного расчёта на дату платежа.

Внутренний контроль `nbki_accounting_snapshot` восстанавливает остаток основного долга непосредственно до и после конкретного платежа из первоначальной суммы займа и уже внесённых частей основного долга в журнале CRM. Он проверяет равенство суммы платежа его частям, отсутствие отрицательного остатка и, только для последней операции, совпадение вычисленного остатка с текущим `loans.balance`. Результат сопровождается ID платежа и не называется нормативной задолженностью ФЛ_25–28: начисленные проценты, сроки, просрочка и момент фактического события требуют отдельного расчёта и проверки.

Также на момент каждого платежа сверяются накопленные суммы по журналу CRM: всего, основной долг, проценты и пени. Они дают проверяемое основание для дальнейшего расчёта блока ФЛ_28, но сами по себе не являются значениями ФЛ_28: для него ещё нужны правила агрегации, кодов соблюдения размера/срока и сверка с нормативной методикой.

Для платежей единого движка v2 дополнительно сверяются неизменные строки `loan_payment_allocations`: суммы по процентам, плановому и досрочному основному долгу, пене и нераспределённой части должны совпасть с записью платежа. Проверяются ссылки на строки графика того же займа. Это доказательство внутреннего разнесения CRM, но не исторический нормативный срез по ФЛ_25–28. Текущий `loan_schedule` меняется при перерасчётах и не должен задним числом приниматься за его состояние в день старого платежа.

С 29.10.2026 новые платежи v2 сохраняют `nbki_recorded_at` — момент регистрации в CRM с часовым поясом. Это **не** дата и время наступления события. Для ручных обычных и досрочных платежей оператор может дополнительно указать подтверждённое фактическое время приёма в МСК; оно сохраняется отдельно в `nbki_event_occurred_at` с основанием `operator_entered`. Если время неизвестно, поле остаётся пустым. Прежние платежи не получили вымышленный backfill. Банковский импорт пока содержит только календарную дату (`operation_date` с техническим `00:00`), поэтому автоматически не утверждает точное время платежа.

Письмо Банка России от 20.02.2026 № 44-8-1/1069 требует отражать фактический момент события, а не момент формирования кредитной информации: https://www.cbr.ru/Content/Document/File/187264/20260220_44_8_1-1069.pdf. Указание `00:00:00+00:00` предусмотрено только для перечисленных в письме случаев, включая событие, которое законом или договором определено только датой. Для обычного платежа произвольное `HH:MM:SS+03:00` не является допустимым способом восполнить неизвестное время. Требуется согласовать подтверждённую методику для старых платежей и банковского импорта.
